How to read this

What the timeline shows

The threshold is a reconnect window

FastStartFailoverThreshold is how long the master observer keeps trying to reconnect, counted from the moment it first lost the connection, not a timeout on a single ping. That moment is t = 0 here.

Both the observer and the standby must have lost the primary

Fast-start failover requires the observer and the target standby to have both lost the primary for the threshold. If the standby can still reach the primary, there is no failover.

Readiness depends on the protection mode

In MaxAvailability and MaxProtection the standby must have been synchronized at failure time. In MaxPerformance its apply lag must be at or below FastStartFailoverLagLimit. If the check fails, failover is not permitted.

No broker property shortens execution

Once initiated, the standby applies the redo it already holds, converts to the primary role, and opens read-write. That span depends on the apply lag at failure time and on the environment.

The ping properties override the threshold

Per the broker documentation, FastStartFailoverThreshold is ignored when ObserverPingRetry and ObserverPingInterval are set. Detection then costs interval × (retries + 1), about a second at the minimums.

An isolated primary runs its own clock

Cut off from both the observer and the standby, the primary stalls (V$DATABASE.FS_FAILOVER_STATUS goes to STALLED) and, if FastStartFailoverPmyShutdown is TRUE, aborts itself after one threshold.

In a switchover, t = 0 is a command

t = 0 is a DBA issuing SWITCHOVER TO in DGMGRL; nothing has to be detected, so no clock runs and neither FastStartFailoverThreshold nor the ObserverPing properties are consulted. The observer stays connected only so fast-start failover remains enabled across the swap.

A switchover loses nothing, in any mode

The roles swap only once the target holds all the redo — the catch-up band on the timeline; an apply lag lengthens it but costs no data. With fast-start failover enabled the broker allows a switchover only to the target standby, and in MaxPerformance only while the lag is inside FastStartFailoverLagLimit; past that, the command is refused.

The former primary is the one that restarts

Sessions on the primary are terminated when it converts to a standby; the downtime window runs from that moment to the new primary’s read-write open. The broker restarts the old primary in its new role and starts Redo Apply — the documentation is explicit that the new primary does not need to be restarted and does not wait for the old one.

No observer, no fast-start failover

The primary still commits and the standby still applies, but V$DATABASE.FS_FAILOVER_STATUS reads PRIMARY UNOBSERVED, FS_FAILOVER_OBSERVER_PRESENT reads NO, and the broker raises ORA-16820. 19c registers up to three observers; if the master is lost while primary and standby stay connected, the broker promotes a backup on its own.

A third site is what arbitrates a partition

When only the link between the two database sites fails, an observer at a third site still reaches the primary. No threshold ever starts, nothing is promoted, and a healthy primary keeps serving — the case Oracle’s first placement recommendation is written for.

The same partition, an observer beside the standby

Move the observer into the standby’s site and the cut takes it away with the standby. Both clocks run out and the standby is promoted; the primary, which never stopped serving, stalls and — with FastStartFailoverPmyShutdown TRUE — aborts itself at the threshold.

Losing the standby site can stop the primary

An observer in the standby’s data centre dies with it. The primary then reaches neither the observer nor the standby, so it stalls from t = 0 and aborts itself one threshold later — with no standby left to promote. The spare site takes production down with it.

Deploying no observer is not the same as losing one

With no observer in the topology, fast-start failover is never enabled: the FastStartFailover* properties can be set, but nothing arms them. FAILOVER TO still works — it is always available, and it is the only thing that promotes the standby.

Transport layer · one commit

What one commit costs — SYNC, FASTSYNC, ASYNC

Transport cost is paid on every commit, for as long as the configuration runs. The broker property is LogXptMode (SYNC, FASTSYNC or ASYNC); the three differ by one disk write on the standby and one round trip on the wire. Measuring the cost from an AWR report is chapter 5.

AFFIRM means the redo is on disk

SYNC sets SYNC + AFFIRM: the destination acknowledges redo only after writing it to the standby redo log. FASTSYNC sets SYNC + NOAFFIRM: it acknowledges before that write. Under both, a commit waits for the acknowledgement; all three values require standby redo logs.

FASTSYNC drops the standby disk wait

Since 12.1, maximum availability mode only. It saves the standby redo log write, but only while the network is the bottleneck: once the local write outlasts the round trip, the chip above reads zero. The broker documents that fast-start failover cannot be initiated while FASTSYNC is in use and the standby is missing redo data.

ASYNC never waits for the standby

Under ASYNC + NOAFFIRM, the broker default, a commit never waits for the destination: it costs the local write alone. Redo still on the wire is the exposure, which is why MaxPerformance gates fast-start failover on FastStartFailoverLagLimit. The broker lists ASYNC for MaxPerformance and SYNC/FASTSYNC for MaxAvailability; MaxProtection is out of scope here.

Transport layer · after the drop

The destination is dropped — ReopenSecs and MaxFailure decide when redo flows again

This panel starts after the failure: NET_TIMEOUT expired, the error was logged, the transport session was terminated, and LOG_ARCHIVE_DEST_2 is closed (panel A of where NET_TIMEOUT fits, chapter 5). The primary stays open read-write. ReopenSecs sets how soon transport may retry the destination, MaxFailure whether it ever stops trying; the protection mode, inherited from chapter 1, changes what the outage costs fast-start failover, never when the destination reopens. Drawn in minutes.

The gap is at least ReopenSecs

Nothing reopens a failed destination sooner than one ReopenSecs. The property decides eligibility; the retry itself fires at the first log switch after the interval expires, so a busy database recovers faster than a quiet one. REOPEN applies to every error, not only connection failures.

MaxFailure disables the destination

MaxFailure counts consecutive reestablish attempts at log switches; default 0 means unlimited. Reaching the limit disables the destination — no further access until it is manually reenabled, and REOPEN is then treated as unspecified. One documented exception: destinations with the 12.2 GROUP and PRIORITY attributes re-enter service on their own.

The lag limit expires during the outage

With nothing arriving the standby falls behind in real time: UNSYNCHRONIZED from the first second in MaxAvailability, past FastStartFailoverLagLimit (default 30 s) in MaxPerformance. Either way, no failover is permitted until the destination ships again and the standby resynchronizes.

The application's view

What the application sees, with both databases in one connect string

app_svc runs only where the database is currently primary; the standby's listener refuses instantly with ORA-12514. Scenario, protection mode and clocks are inherited from chapter 1. The timeline follows the worst-case client: a request that starts connecting the moment the service stops being published.

The service name is the switch

A role-based service exists only where the database runs as primary (srvctl add service -role PRIMARY, or a startup trigger on DATABASE_ROLE). Nothing publishes app_svc on the standby, so its listener answers ORA-12514 instantly — the refusal is what makes a two-address string safe.

Every traversal visits the dead address first

With LOAD_BALANCE off the client walks the list in order: every traversal first pays min(TRANSPORT_CONNECT_TIMEOUT, CONNECT_TIMEOUT) on the unreachable host, including every fresh connection after the failover. LOAD_BALANCE = ON randomizes the order and halves the expected cost.

The default string does not retry

RETRY_COUNT defaults to 0: one traversal, then the error goes to the application. The budget — (RETRY_COUNT + 1) × traversal + RETRY_COUNT × RETRY_DELAY — has to reach past the new primary’s open.

Short delays, many retries

Oracle’s HA guidance: a generous CONNECT_TIMEOUT (90 s in the documented example), a transport timeout around a second, and a short RETRY_DELAY with a high RETRY_COUNT. Its switchover sizing example budgets 100 × 3 s.

These parameters govern new connections only

Already-connected sessions end by TCP rules — instant resets from a reachable host, long hangs across a partition — unless keepalives, SQLNET.RECV_TIMEOUT or FAN break them faster; TAF or Application Continuity resumes their work. This panel models new connections only.

In a switchover nothing is unreachable

Both listeners answer throughout, so a planned swap never pays TRANSPORT_CONNECT_TIMEOUT: each traversal is two instant ORA-12514s, about 0.4 s. Only RETRY_COUNT and RETRY_DELAY matter — the default string is finished half a second into a swap that takes half a minute.

When no failover is coming

If the readiness check refuses the failover, the service is never republished: every traversal ends in ORA-12514 and the application stays down until someone intervenes. Retry parameters only extend how long the client keeps trying.

Chapter 5 — Side topics

Side topics · before you turn SYNC on

SDU, socket buffers, and measuring the network before Data Guard uses it

Two Oracle Net settings and one measurement, worth doing before the first SYNC commit: the session data unit (the buffer Oracle Net fills before sending), the socket buffers underneath it (how much can be in flight at once), and oratcptest, which makes the same round trip redo transport will make.

SDU is the unit Oracle Net ships

SDU is how much data Oracle Net buffers before sending; default 8192 bytes, range 512 bytes to 2 MB. It is negotiated per connection and the smaller end wins, so set it on the primary’s transport alias and on the standby’s listener.

65535 is a recommendation for SYNC, not a requirement

Oracle’s HA best practices: SDU = 65535 improved synchronous transport in their testing, and the recommendation is scoped to SYNC only. It is neither a prerequisite (SYNC runs at the default) nor the ceiling (DEFAULT_SDU_SIZE goes to 2 MB).

SEND_BUF_SIZE and RECV_BUF_SIZE are the socket buffers

These two parameters set the TCP socket buffer space Oracle Net requests, on both ends of the link. Defaults are OS-specific (Linux 2.6: 16 KB send, 87380 bytes receive). They go in sqlnet.ora, or per descriptor in tnsnames.ora / listener.ora at DESCRIPTION or ADDRESS level. The value is a request; the OS may grant less.

How big: the bandwidth-delay product

BDP = link capacity × round-trip latency. Net Services asks for buffers of at least one BDP (its worked example: 100 Mbit/s at 5 ms ≈ 64 KB, or up to the largest redo message); the HA guide raises that to 3 × BDP for a high-latency, high-bandwidth network. Buffer space is charged per connection — check the total across concurrent connections.

oratcptest makes the round trip for you

oratcptest.jar is MOS note 2064368.1: JRE 6+, any OS user, no database — one process listens on the standby host, another sends from the primary. SYNC mode waits for each acknowledgement, the shape of a SYNC commit; ASYNC mode never waits.

Double the buffer sizes it reports

Each run reports the socket buffer size it got — the figure to compare against the BDP. Two warnings from the guide: the tool reports half the allocated buffer, so double it, and do not set -sockbuf, which answers to different kernel parameters than the ones the test otherwise exercises.

Side topics · after you turn SYNC on

What a commit waits for — log file sync and the events inside it

Turn SYNC on and the log file sync average moves first — the number Oracle warns not to judge SYNC by. The events nest; reading an AWR report means knowing which contains which.

Each name covers a different span

log file sync is the whole cycle the committing session sees. Inside it, redo write time covers LGWR’s write; inside that run the two legs, log file parallel write (local) and SYNC remote write. LGWR starts the remote write first and waits for it after the local one, so a commit pays the longer leg, not both.

One of the five is not a wait event

redo write time is a V$SYSSTAT statistic in centiseconds, not a wait event. Multiply a per-write average from it by ten before comparing it with a wait event’s millisecond average.

The average misleads

Oracle does not recommend judging SYNC by log file sync wait times: commits are batched, one slow write makes many sessions wait, and the average follows the outliers. Watch the transaction rate and redo rate from AWR for OLTP, elapsed time for batch; read the event as a histogram.

Measure before and after on the same workload

Capture the same AWR metrics on the same workload before and after enabling SYNC. Oracle’s worked example: redo rate unchanged, log file sync average 0.68 ms to 4.60 ms, transactions per second down 20.3%, redo writes down 61% with the average write up 94% (commit batching). Their numbers, not a prediction for yours.

Watching the lag afterwards

V$DATAGUARD_STATS carries the transport and apply lag; read DATUM_TIME beside them — on a quiet configuration a lag can be older than it looks. V$STANDBY_EVENT_HISTOGRAM keeps the history.

Side topics · when the ack stops coming

Where NET_TIMEOUT fits, and where it does not

NET_TIMEOUT (broker property NetTimeout) is a LOG_ARCHIVE_DEST_n attribute on the primary, not a failover clock: it caps how long LGWR waits for a SYNC acknowledgement before the error is logged, the transport session terminated, and the destination dropped. Both it and FastStartFailoverThreshold default to 30 s, which is why the two get confused; the panels span the same window, and panel B shortens NET_TIMEOUT to 10 s to show why data still is not lost.

“NET_TIMEOUT 10 s, threshold 30 s — do I lose 20 s of redo?”

No. NET_TIMEOUT expiring only brings the primary to a decision point; whether it may continue without its standby is a separate check, and an isolated primary fails it.

Continuing alone requires the observer or the standby

With fast-start failover enabled, a MaxAvailability primary may drop to UNSYNCHRONIZED and keep committing only while it can reach the observer or the target standby. In panel A the observer is reachable, so it carries on; in panel B nobody answers, so redo generation stalls (FS_FAILOVER_STATUS = STALLED).

Why the failover still loses nothing

Under SYNC a commit is not acknowledged until the standby holds its redo, so every acknowledged transaction is on the standby when it opens. Commits issued during the stall hang until the old primary aborts, then get errors — nothing is lost silently. A shorter NET_TIMEOUT only moves when the hanging starts.

In MaxPerformance (ASYNC) commits never wait for the standby, so NET_TIMEOUT never touches user sessions and never appears on the failover timeline; eligibility and data loss are bounded by FastStartFailoverLagLimit instead.
