### A. Far sync

- A1 [D] 19c C&A ch.5 https://docs.oracle.com/en/database/oracle/oracle-database/19/sbydb/creating-oracle-data-guard-far-sync-instance.html
  "A far sync instance manages a control file, receives redo into standby redo logs (SRLs), and archives those SRLs to local archived redo logs" — "does not have user data files, cannot be opened for access, cannot run redo apply, and can never function in the primary role or be converted to any type of standby database." Far sync instances have no broker *states*. "Standby redo log files used at the far sync instance cannot be shared with other databases." **"there must still be a direct network connection between the primary database and the remote standby database ... used to perform health checks and switchover processing tasks."** (a far-sync edge does not replace the primary↔standby link). Requires Active Data Guard licence.
- A2 [D] primary→far sync: SYNC ("all committed redo resides on disk at the far sync instance"); MaxPerformance uses ASYNC into the far sync. FASTSYNC allowed per broker FSFO prereq (19c broker ch.5 https://docs.oracle.com/en/database/oracle/oracle-database/19/dgbkr/using-data-guard-broker-to-manage-switchovers-failovers.html): "To use a far sync instance with fast-start failover, the far sync instance transport mode must be set to either SYNC or FASTSYNC and the target standby database transport mode must be set to ASYNC."
- A3 [D] far sync→terminal: "uses ASYNC transport to ship the incoming redo to terminal standbys". Required ASYNC under FSFO. SYNC onward: [UNDOC] — word as "documented as ASYNC", never "forbidden".
- A4 [CONFLICT] protection modes: C&A ch.5 "supported in either maximum performance or maximum availability mode" (no mention of MaxProtection). Broker ch.4 https://docs.oracle.com/en/database/oracle/oracle-database/19/dgbkr/managing-oracle-data-guard-broker-configuration-members.html : MaxProtection cannot be used "If a far sync instance is the only configuration member receiving redo in synchronous mode from the primary database". Broker ch.5 FSFO prereqs (19c): "A far-sync instance cannot be used in maximum protection mode or maximum performance mode." 26ai (https://docs.oracle.com/en/database/oracle/oracle-database/26/dgbkr/fast-start-failover2.html): "...cannot be used in maximum protection mode." (MaxPerformance dropped). FSFO chapter table: far sync supported to send redo — MaxProt No / MaxAvail Yes / MaxPerf No (this is the *FSFO* table). "Far sync in MaxProtection from 12.2" is [UNDOC] (12.2 change is FSFO in MaxProtection, not far sync).
- A5 RedoRoutes [D] 12.1 broker ch.4 https://docs.oracle.com/database/121/DGBKR/dbresource.htm ; introduced 12.1.0.1, alternate 12.1.0.2 (https://docs.oracle.com/database/121/DGBKR/release_changes.htm). Grammar: `(redo source : redo destination)`; source `LOCAL|ANY|name[,name]`; dest `ALL [attr] | name [attr][,name [attr]]`; attr `ASYNC|SYNC|FASTSYNC`; 12.1 alternate `ALT=(name [xpt] [FALLBACK])`. "LOCAL ... cannot be used at a far sync instance." A source may appear in only one rule per member. Unspecified attr → dest's LogXptMode. Default NULL == `(LOCAL : ALL)` at a primary. "A redo routing rule is active if its redo source field specifies the current primary database." "The ASYNC redo transport attribute must be explicitly specified for a cascaded destination to enable real-time cascading." Cannot be set on snapshot standby; logical standby only with LOCAL destination [CONFLICT within page]. Alternate needs non-zero MaxFailure on the non-alternate member. 26ai grammar (https://docs.oracle.com/en/database/oracle/oracle-database/26/dgbkr/redo-routing-rules.html) uses parenthesised destination groups with `PRIORITY=n`, n=1..8, default 1 for far sync members, 8 otherwise; no ALT/FALLBACK. **[D, 19c — re-verified 2026-08-17]** the 19c broker properties page (https://docs.oracle.com/en/database/oracle/oracle-database/19/dgbkr/oracle-data-guard-broker-properties.html, *RedoRoutes* → *Redo Routing Rules*) carries the same PRIORITY grammar word for word: `{ db_unique_name_1 [xpt_mode] | ( db_unique_name_1 [xpt_mode] [PRIORITY=n] [,db_unique_name_n [xpt_mode] [PRIORITY=n]] ) }`, "The optional [PRIORITY=n] can have n =1 ~ 8. The default value for far sync members is 1 and the default value for non-far sync members is 8", "Setting PRIORITY=8 has special meaning. If a primary ships redo to a destination with PRIORITY=8, then it must ship to every PRIORITY=8 destination", plus the LOCAL/ANY/source-once/default-NULL/active-rule/ASYNC-for-real-time-cascade/snapshot/logical usage notes — so PRIORITY and those notes are 19c facts, and 19c broker ch.4 Example 4-3 uses the form. The 19c property table lists *Standby type: Physical standby and far sync instance* while its usage notes allow a logical standby with a LOCAL source — that is the [CONFLICT within page]. **`GROUP` is a LOG_ARCHIVE_DEST_n attribute, not RedoRoutes syntax.** 26ai *RedoRoutes property* page (https://docs.oracle.com/en/database/oracle/oracle-database/26/dgbkr/redoroutes.html — the property page, not the Redo Routing Rules page): "A member whose MaxFailure property is set to zero cannot be part of a RedoRoutes group"; not on the 19c page. Canonical pair, from 19c broker ch.4 *Managing Far Sync Instances*: `EDIT DATABASE 'North_Sales' SET PROPERTY 'RedoRoutes' = '(LOCAL : FS1 SYNC)'; EDIT FAR_SYNC 'FS1' SET PROPERTY 'RedoRoutes' = '(North_Sales : South_Sales ASYNC)';`
- A6 FSFO with far sync [D]: "the target standby cannot be a far-sync instance. However the target can receive redo from a far sync instance." FastStartFailoverTarget "can only be set to the name of physical or logical standbys. It cannot be set to the name of a snapshot standby database, far sync instance, or Zero Data Loss Recovery Appliance." How SYNCHRONIZED is computed across the far-sync hop: [UNDOC] → label as this page's model. Observer connectivity documented only to primary + target standby; observer→far sync [UNDOC].
- A7 far sync failure [D]: "If the far sync instance fails, then redo should be shipped directly to the terminal standby by adding an additional log archive destination ... Examples 5-2..5-5 (alternate, fan-out PRIORITY=8, HA far sync pair, second far sync near the standby for role-change readiness). Broker: `ADD FAR_SYNC FS2 AS CONNECT IDENTIFIER IS FS2.example.com; EDIT FAR_SYNC 'FS2' SET PROPERTY 'RedoRoutes' = '(South_Sales : North_Sales ASYNC)'; ENABLE FAR_SYNC FS2; EDIT DATABASE 'South_Sales' SET PROPERTY 'RedoRoutes' = '(LOCAL : FS2 SYNC)';` → **routes are pre-declared for both directions; nothing rewrites on role change.** MaxAvailability continuing when the far sync dies: two documented pieces (MaxAvail "operates as if it were in maximum performance mode" without ack from at least one synchronized standby, https://docs.oracle.com/en/database/oracle/oracle-database/19/sbydb/oracle-data-guard-protection-modes.html ; NET_TIMEOUT) — composition is the page's model.
- A8 DGMGRL [D] https://docs.oracle.com/en/database/oracle/oracle-database/19/dgbkr/oracle-data-guard-broker-commands.html : `ADD FAR_SYNC name AS CONNECT IDENTIFIER IS ci; ENABLE FAR_SYNC; EDIT FAR_SYNC ... ### B. Cascading

- B1 [D] C&A §7.3 https://docs.oracle.com/en/database/oracle/oracle-database/19/sbydb/oracle-data-guard-redo-transport-services.html : terminal destination "receives primary database redo indirectly from a standby database"; cascading standby applies and forwards; offloads transport from the primary.
- B2 [D] "up to 30 terminal destinations"; real-time (from SRL) vs non-real-time (archived SRLs). Restrictions (complete list): only physical standbys cascade; real-time needs Active Data Guard; non-real-time on destinations 1–10 only. Depth limit: [UNDOC]. Cascader→terminal transport: [D] C&A §7.3.1 (the cascading standby's own LOG_ARCHIVE_DEST_n): "If you specify ASYNC transport mode on destinations 1 through 10, then redo is shipped in real-time. If you do not specify a transport mode or you specify SYNC on destinations 1 through 10, then redo is shipped in non-real-time. Destinations 11 through 31 operate only in ASYNC (real-time) transport mode." (verified 2026-08-17; SYNC is documented as non-real-time, not UNDOC). Cost of the cascader's SYNC wait: [UNDOC]. Whether protection mode considers cascaded destinations: [UNDOC] (inference: no).
- B3 FSFO target: fails the direct-redo prerequisite (deduction from two documented sentences; no literal prohibition). **Manual failover to a terminal standby is documented**: "no attempt is made to transmit any unsent redo from the cascader to the terminal standby." Switchover to terminal: [UNDOC].
- B4 [D] 19c broker ch.4 Ex 4-2: `(LOCAL : Local_Sales SYNC)` on primary, `(North_Sales : Remote_Sales ASYNC)` on Local_Sales; SHOW CONFIGURATION shows cascade by indentation and `(receiving current redo)`. Ex 4-3 PRIORITY alternates + `(alternate of Local_Sales)`.

### C. Multiple standbys / FSFO targets

- C1 [D] multi-target new in 12.2 (https://docs.oracle.com/en/database/oracle/oracle-database/12.2/dgbkr/release-changes.html). 19c: "candidate targets. The broker selects a target based on the order in which they are specified"; "If the designated fast-start failover target develops a problem ... the broker automatically changes the fast-start failover target to one of the other candidate targets"; with >1 standby the property must be set explicitly. Property: names or `ANY`; "Targets are verified when fast-start failover is enabled"; reciprocal value on the target set automatically. Physical or logical only. 19c: `SET FAST_START FAILOVER TARGET TO name [NOWAIT]` (dynamic retarget). `SHOW FAST_START FAILOVER` shows Active Target / Potential Targets / per-target valid flag. **Do not write "first viable in list order".**
- C2 [D] bystanders: `BystandersFollowRoleChange` default ALL; viability check on complete failover. Observer treatment of non-targets: [UNDOC] (observer pings primary + target only).
- C3 MaxProtection: C&A protection-modes page: "shuts the primary database down rather than allowing it to continue"; "Oracle recommends that a minimum of two standby databases be used ... to prevent a single standby database failure from causing the primary database to shut down". [D] 19c broker ch.4 (members page, *Maximum Protection*, verified 2026-08-17): "the primary database will shut down, rather than continue processing transactions, if it cannot write its redo stream to at least one synchronized standby database" and "If only one standby database is supporting maximum protection mode, Oracle Data Guard broker will disallow the shutdown of the apply instance." So "any one SYNC ack suffices" is documented in the broker guide's wording; the C&A page's own MaxProtection paragraph does not spell out "at least one" (its MaxAvailability paragraph does, C4). Cite the broker page for it.
- C4 [D, explicit] MaxAvailability: "If the primary does not receive acknowledgement from at least one synchronized standby, then it operates as if it were in maximum performance mode".

### F. RAC members (verified 2026-09-28)

Fetched 2026-09-28 in full from the 19c broker guide (members chapter https://docs.oracle.com/en/database/oracle/oracle-database/19/dgbkr/managing-oracle-data-guard-broker-configuration-members.html, properties page https://docs.oracle.com/en/database/oracle/oracle-database/19/dgbkr/oracle-data-guard-broker-properties.html, concepts chapter https://docs.oracle.com/en/database/oracle/oracle-database/19/dgbkr/oracle-data-guard-broker-concepts.html).

- F1 [D] RAC primary (concepts, *Benefits*): "From an Oracle Data Guard perspective, the primary database remains available as long as at least one instance of the clustered database continues to transport redo data to the standby databases." "If the last instance of the primary database fails, and fast-start failover is enabled, the broker can continue to provide high availability by automatically failing over to a pre-determined standby database." Table 4-1 TRANSPORT-ON: "If this is an Oracle RAC database, all instances open in read/write mode will have redo transport services running." Which instance ships which redo thread, and how a surviving instance covers a failed one's thread: not modelled.
- F2 [D] RAC standby apply instance (members chapter, Table 4-1 APPLY-ON): "If the standby database is an Oracle RAC database, the broker starts Redo Apply on exactly one standby instance, called the apply instance. If this instance fails, the broker automatically chooses another instance that is either mounted or open read-only. This new instance then becomes the apply instance." Logical standby: "SQL Apply is running on one instance, the apply instance. If this instance fails, the broker automatically chooses another open instance." *Apply Services in an Oracle RAC Database Environment*: "If the apply instance fails, then the broker automatically restarts SQL Apply, or the Redo Apply coordinator, as appropriate, on a different instance. This is called apply instance failover". Multi-instance Redo Apply (`ApplyInstances`, 12.2+) exists; the page draws single-instance apply, the broker default (`ApplyInstances` default 0 = "recovery will be started in single instance mode").
- F3 [D] selection: "If you have no preference which instance is to be the apply instance in an Oracle RAC standby database, the broker randomly picks an apply instance." After a failure: "if the PreferredApplyInstance property indicates an instance that is currently running, select it as the new apply instance; otherwise pick a random instance that is currently running to be the new apply instance." "Once the apply instance is selected and, as long as the apply instance is still running, the broker disregards the value of the PreferredApplyInstance property even if you change it." It is only used when the database is a standby Oracle RAC database. The value could be an empty string (default) which means the broker chooses the apply instance." Standby type physical, logical. `ApplyInstanceTimeout` — "specifies the number of seconds the broker waits after detecting the current apply instance failed before initiating the apply instance failover"; valid values >= 0; broker default 0 "(results in immediate apply instance failover)".
