# Fact check: `simulator/fsfo-simulator.html` (English)

Date: 2026-08-01  
Scope: the English static text, English strings generated by JavaScript, four pure timing models, generated configuration snippets, and the corresponding invariants in `site/test.mjs`. Czech translation quality is out of scope. The review used Oracle documentation as the normative source. Login-gated MOS material is called out separately.

## Bottom line

The 19c transport, Oracle Net, SDU/socket-buffer, wait-event, and basic FSFO explanations are mostly accurate. The most important errors are concentrated in the 26ai additions and observer-state model:

1. The 26ai model incorrectly preserves the 19c MaxAvailability rule. In 26ai, a nonzero `FastStartFailoverLagLimit` permits bounded-loss FSFO in MaxAvailability; the simulator disables the control and always requires synchronization/zero loss.
2. `PrimaryDatabaseCandidates` is described almost backwards. It restricts broker switchovers/failovers when FSFO is **disabled**; an excluded broker manual failover is rejected with ORA-16529; when FSFO is enabled it adds no restriction beyond the FSFO target mechanism.
3. The “both database sites” observer behavior is partly an unsupported inference. The broker documents automatic backup nomination when primary and target remain connected after loss of the master observer. The simulator applies nomination across a site partition/isolation where that precondition is absent.
4. “No observer” prose mixes FSFO-disabled and FSFO-enabled-but-unobserved states and reports `PRIMARY UNOBSERVED` on the wrong side.
5. The core “both observer and standby must lose the primary” rule silently assumes the default `ObserverOverride=FALSE`.

The source test passes **65/65**, but it is a consistency guard. Several passing tests encode the factual problems above.

### Verdicts

- **Correct**: supported by the cited Oracle source, including clearly disclosed drawing assumptions.
- **Needs nuance**: materially right only under an unstated condition, edition, query location, or idealization.
- **Incorrect**: conflicts with Oracle documentation.
- **Unverifiable**: no official Oracle source found, or the claim depends on MOS/lab behavior not available in this audit.

## Recommended correction order

1. Fix 26ai MaxAvailability LagLimit semantics across controls, model, drawings, generated DGMGRL, prose and tests.
2. Correct `PrimaryDatabaseCandidates` and remove/verify the 19.26 backport claim.
3. Remove the asserted both-sites partition/isolation outcomes until a 26ai runtime test confirms them; stop gating both-site topology itself to 26ai.
4. Separate FSFO-disabled/no-observer from enabled-but-unobserved and make status query-side explicit.
5. Declare `ObserverOverride=FALSE` as the scope or model it.
6. Apply the narrower prose fixes: AutoReinstate prerequisites, manual-failover availability, TAF vs AC, `NET_TIMEOUT`, VALIDATE placement, ping equation, and observer-view clock wording.

No simulator source was changed by this fact-check.
